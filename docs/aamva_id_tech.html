1. Service overview

AAMVA Parsing Services is a standards-aware decoding engine for U.S. and Canadian driver licenses and ID cards. It ingests raw magstripe tracks, PDF417 barcodes, or pre-scanned strings and returns a clean, normalized JSON payload suitable for guest intake, KYC, access control, and other identity-driven workflows.

The service is designed as a thin, deterministic layer: it does not guess, embellish, or infer beyond what the AAMVA payload provides. Instead, it focuses on consistent parsing, jurisdiction-aware normalization, and full operational traceability.

Core goals:

  • Provide a reliable, vendor-agnostic AAMVA decoding surface.
  • Normalize heterogeneous card formats into a stable JSON schema.
  • Handle state-specific quirks and legacy formats without breaking downstream systems.
  • Expose a small, clear API surface for operational products.
  • Keep the implementation inspectable, testable, and easy to embed.

2. Input formats

2.1 Magstripe tracks

The service supports all three AAMVA magstripe tracks:

  • Track 1: Name, address, city, state, postal code.
  • Track 2: ID number, expiration, DOB, checksum fields.
  • Track 3: Optional jurisdiction/vendor-defined fields (restrictions, endorsements, organ donor, audit numbers).

Typical input example:

%MAGSTRIPE_TRACK_1_STRING_HERE?
;MAGSTRIPE_TRACK_2_STRING_HERE?
+MAGSTRIPE_TRACK_3_STRING_HERE?

2.2 PDF417 2D barcode

PDF417 is treated as the canonical AAMVA payload when available. The parser reads the full data block, including jurisdiction-specific subfiles and extensions.

2.3 Auto-detect mode

For environments where the upstream device may send mixed formats, an auto-detect mode inspects the payload and routes it to the appropriate magstripe or PDF417 parser.

3. Parsing model

3.1 Standards alignment

The engine follows AAMVA DL/ID Card Design Specifications, including field identifiers (e.g., DAA, DCS, DCT), date formats, and jurisdiction-specific subfile structures. Where multiple spec versions exist, the parser uses version markers in the payload to select the correct ruleset.

3.2 Normalized output schema

All inputs are mapped into a stable JSON structure:

{
  "name": { "first": "JOHN", "last": "SAMPLE", "middle": "PUBLIC" },
  "dob": "1984-11-22",
  "idNumber": "D01111111",
  "address": {
    "street": "1234 E MAIN ST",
    "city": "PHOENIX",
    "state": "AZ",
    "zip": "85001"
  },
  "expiration": "2026-11-19",
  "issueDate": "2015-11-15",
  "jurisdiction": "AZ",
  "restrictions": [],
  "endorsements": [],
  "class": "D",
  "organDonor": true,
  "raw": ""
}

3.3 Deterministic behavior

The parser is intentionally deterministic: the same input always yields the same output. Ambiguous or malformed fields are surfaced explicitly via warnings and error codes rather than silently coerced.

4. Validation, errors, and logging

4.1 Validation layer

The validation layer performs:

  • Date checks: DOB, expiration, and issue dates are validated and normalized to YYYY-MM-DD.
  • Field presence: Required identifiers (e.g., ID number, name, jurisdiction) are checked and flagged if missing.
  • Jurisdiction rules: State/province-specific constraints (e.g., length of ID numbers, class codes) are applied where known.

4.2 Error model

Errors are structured, not ad hoc:

{
  "success": false,
  "code": "INVALID_DATE_FORMAT",
  "message": "DOB could not be parsed from field DBB",
  "field": "dob",
  "rawValue": "1984/11/22"
}

4.3 Audit log

Every parse operation can be logged with full before/after context. The log captures timestamps, input source, normalized output, and any warnings or errors, enabling forensic reconstruction of identity decisions. 

[2026-03-23T16:01:12Z] PARSE /pdf417 • AZ • success • id=D01111111

5. API surface

AAMVA Parsing Services exposes a small REST-like API that can be embedded in local apps, edge services, or centralized backends.

5.1 Endpoints

  • POST /parse/magstripe
  • POST /parse/pdf417
  • POST /parse/auto
  • GET /health
  • GET /specs/jurisdictions
  • GET /logs/recent (optional, when logging is enabled)

5.2 Request / response

Example request:

POST /parse/pdf417
{
  "payload": "@ANSI 6360..."
}

Example success response:

{
  "success": true,
  "data": {
    "name": { "first": "JOHN", "last": "SAMPLE" },
    "dob": "1984-11-22",
    "idNumber": "D01111111",
    "jurisdiction": "AZ",
    "expiration": "2026-11-19"
  },
  "warnings": []
}

Example response with warnings:

{
  "success": true,
  "data": { ... },
  "warnings": [
    {
      "code": "UNKNOWN_FIELD",
      "field": "ZAA",
      "message": "Unrecognized jurisdiction-specific field"
    }
  ]
}

6. Integration scenarios

6.1 Hospitality & guest intake

At check-in, a magstripe or PDF417 swipe populates guest name, address, DOB, and ID number directly into the registration workflow. The parsing layer becomes a trusted, low-friction identity capture step that feeds the hotel OS or PMS.

6.2 KYC & financial services

In KYC flows, the parser feeds normalized identity data into verification pipelines, watchlist checks, and risk engines. Deterministic output simplifies matching and reduces false positives from inconsistent formatting.

6.3 Access control & security

Secure facilities can use the service to validate IDs at entry points, logging each parse alongside access decisions for later review.

6.4 Transportation & logistics

Driver onboarding and compliance checks can be automated by parsing license data into fleet management systems, ensuring that class, endorsements, and restrictions are captured accurately.

7. Deployment & performance

The parsing engine can run fully local (browser, desktop, or edge device) or as a centralized service. Local deployment keeps raw ID data on-device, while centralized deployment simplifies fleet management and monitoring.

  • Latency: Sub-10ms parse times for typical magstripe and PDF417 payloads.
  • Throughput: Designed for bursty, operator-driven workloads rather than bulk batch processing.
  • Footprint: Small, dependency-light core suitable for embedding.

8. Roadmap

Planned extensions on top of the core AAMVA parser include:

  • Expanded jurisdiction coverage and historical spec versions.
  • Machine-readable zone (MRZ) support for passports and visas.
  • Configurable redaction for sensitive fields (e.g., partial ID numbers).
  • Cloud-hosted, multi-tenant parsing clusters with per-tenant logging.
  • Real-time anomaly detection for fraudulent or synthetic IDs.
  • SDKs for browser, mobile, and server runtimes.

9. Philosophy

AAMVA Parsing Services is built around clarity, operational truth, and predictable structure. It favors explicit mappings, visible rules, and deterministic behavior over opaque heuristics or silent corrections.

The service is intended to be a foundational identity primitive: a small, trustworthy layer that other systems can build on—guest registries, KYC stacks, access control consoles, and beyond. Its job is not to decide, but to decode, normalize, and record the truth of what the card actually says.

10. API samples

This section provides example requests and responses for the core parsing endpoints in AAMVA Parsing Services.

10.1 POST /parse/magstripe

Parse raw magstripe tracks.

POST /parse/magstripe
{
  "track1": "%B1234567890123456^SAMPLE/JOHN^25112010000000000000?",
  "track2": ";1234567890123456=25112010000000000000?",
  "track3": "+;...optional track 3..."
}
{
  "success": true,
  "data": {
    "name": { "first": "JOHN", "last": "SAMPLE" },
    "idNumber": "1234567890123456",
    "expiration": "2025-11-20"
  },
  "warnings": []
}

10.2 POST /parse/pdf417

POST /parse/pdf417
{

}
{
