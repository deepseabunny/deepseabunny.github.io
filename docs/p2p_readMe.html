P2P Node Mesh Simulator

A browser‑based simulator that models a small peer‑to‑peer mesh. Each node runs in the same page, has its own IndexedDB store, and exchanges messages over a socket‑like bus. This README documents the architecture, exact runtime behavior, UI controls, technical operations, JSON examples, and troubleshooting steps.

Architecture

The simulator is intentionally simple and client‑side only. It is composed of three main parts:

  • Node UI — a card representing a peer with controls for sending, syncing, and toggling online state.
  • IndexedDB per node — each node stores messages in a database named p2p_node_{id}.
  • SocketBus — a hybrid broadcast layer using BroadcastChannel plus direct local handler invocation to guarantee same‑page delivery.

Databases and Stores

Each node uses an IndexedDB database with a single object store:

Database: p2p_node_{id}
Object store: messages
Indexes: createdAt, from_createdAt

Message Model and Operations

Messages and control operations use a small canonical JSON schema. The simulator supports three top‑level operation types: message, sync-request, and sync-response.

Canonical message

{
  "type": "message",
  "from": 1,
  "to": "all",
  "body": "Hello world",
  "createdAt": "2026-04-02T07:00:00.000Z",
  "direction": "outbound",
  "persistedAt": "2026-04-02T07:00:00.050Z"
}

Operation examples

Outbound broadcast (sender constructs and posts):

{
  "type": "message",
  "from": 1,
  "to": "all",
  "body": "Ping from Node 1",
  "createdAt": "2026-04-02T07:00:00.000Z"
}

Sync request (requester asks peers for messages newer than lastSeen):

{
  "type": "sync-request",
  "from": 2,
  "to": "all",
  "lastSeen": "2026-04-02T07:00:00.000Z" // or null to request everything
}

Sync response (peer replies directly to requester):

{
  "type": "sync-response",
  "from": 3,
  "to": 2,
  "messages": [
    {
      "type": "message",
      "from": 3,
      "to": "all",
      "body": "Missed message",
      "createdAt": "2026-04-02T07:05:00.000Z"
    }
  ]
}

Runtime Behavior

The simulator intentionally models a real‑time broadcast mesh without a central store. The exact behavior you will observe is described below.

Normal send and receive

  1. Sender persists the message to its own DB (outbound record).
  2. Sender calls socketBus.send(payload).
  3. SocketBus posts to BroadcastChannel (cross‑tab) and invokes local handlers directly (same‑page).
  4. Each online peer receives the payload, persists an inbound record, and updates UI.

Offline handling

By design, when a node is toggled offline it stops processing incoming broadcasts. The node does not buffer, queue, or persist messages while offline. Messages sent while a node is offline are not automatically recovered.

Sync history behavior

The Sync History control currently performs a local read of the node's IndexedDB and refreshes the UI. It does not contact peers or request missed messages unless a sync protocol (sync‑request / sync‑response) is implemented and enabled.

Scenario Walkthroughs

Scenario A: Real‑time delivery

1. Node 1 sends "Hello"
2. Node 2 and Node 3 are online
3. Node 2 and Node 3 receive and persist the message
4. All three nodes show the message in their history

Scenario B: Offline gap

1. Node 1 sends "Hello"
2. Node 2 receives it
3. Node 2 goes offline
4. Node 3 sends "Missed A" and "Missed B"
5. Node 2 clicks Sync History
6. Node 2 sees only messages it persisted earlier; "Missed A" and "Missed B" are not present

Reason: Sync History reads local DB only; Node 2 never persisted Node 3's messages while offline.

Sync Protocol Design (optional extension)

To recover missed messages, implement the following peer‑to‑peer catch‑up protocol:

  1. Requester computes lastSeen (latest createdAt it has) and broadcasts a sync-request.
  2. Peers query their DB for messages with createdAt > lastSeen and reply with a sync-response addressed to the requester.
  3. Requester persists incoming messages (dedupe by from + createdAt) and refreshes UI.

UI Controls and Exact Effects

Control Effect
Add Node Creates a new node card, subscribes to socket bus, DB created on demand
Clear All IndexedDB Deletes all p2p_node_{id} databases and clears UI
Send Persist locally, broadcast via socket bus, refresh sender UI

Sync history Reads local DB and refreshes UI; does not contact peers unless sync protocol is added

Troubleshooting

If messages are not appearing on other nodes

  • Confirm receiving nodes are online (status pill shows Online).
  • Open DevTools console and watch for logs from sendMessage, socketBus.onMessage, and refreshHistory.
  • Ensure BroadcastChannel is available in your environment; the bus also invokes local handlers directly for same‑page delivery.
  • Check for IndexedDB errors in the console (permissions, blocked deletes, open connections).

If Sync history shows no new messages after offline period

  • Understand that Sync history reads local DB only; missed messages must be recovered via a sync protocol.
  • Implement the sync‑request / sync‑response flow described above to enable catch‑up.

Extensions and Next Steps

  • Implement the sync protocol to recover missed messages.
  • Add selective routing so to can be a node id instead of "all".
  • Introduce a lightweight relay or WebSocket backend for multi‑device persistence.
  • Use CRDTs for conflict‑free replicated state beyond simple message logs.
  • Add encryption and signatures for message authenticity.
